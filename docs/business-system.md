# ビジネス化システム設計書

「自分用ツールを都度指示で作る」段階から、
「マルチエージェントで回るビジネス検証システム」へステップアップするための設計。

## 全体像

```mermaid
flowchart LR
    A[アイデア<br>business/ideas.md] --> B[調査<br>market-researcher]
    B -->|参入余地あり| C[実装<br>product-builder]
    B -->|余地なし| A
    C --> D[品質ゲート<br>quality-reviewer]
    D -->|OK| E[公開・告知<br>publisher]
    D -->|NG| C
    E --> F[計測・記録<br>validation-log.md]
    F --> G[週次レビュー<br>weekly-review.md]
    G -->|継続/変更/撤退| A
```

一周 = 1つの検証。このループを小さく速く回すことが目的。
一発で当てるシステムではなく、外れを速く安く捨てるシステム。

## マルチエージェントの使い方

`.claude/agents/` に4役を定義済み。Claude Codeでの頼み方の例:

| やりたいこと | 頼み方の例 |
|---|---|
| アイデアの調査 | 「market-researcher でアイデア#1を調査して、結果をideas.mdに記録して」 |
| 機能の実装 | 「product-builder でコード進行練習機能を追加して」 |
| 公開前チェック | 「quality-reviewer で index.html を公開前レビューして」 |
| 公開・告知準備 | 「publisher でREADMEと告知文を準備して」 |
| 一周まるごと | 「アイデア#1を検証パイプラインに通して。調査→実装→レビュー→公開準備の順で」 |

最後の「一周まるごと」が本命の使い方。オーナー（あなた）の仕事は
**指示ではなく判断**（調査結果を見て着手可否、レビュー結果を見て公開可否）に絞る。

## 自動化（人がいなくても回る部分）

段階的に自動の比重を上げる。

- **レベル1（今すぐ）:** 上記のパイプライン一括依頼。1回の指示で4エージェントが直列に動く。
- **レベル2（公開後）:** 定期実行（Routines/スケジュール実行）で
  「毎週月曜: アクセス数・Star数を確認して validation-log.md に追記、
  気になる変化があれば通知」を回す。→ 設定はClaude Codeに「週次の計測ルーチンを作って」と言えばよい。
- **レベル3（軌道に乗ったら）:** Issue駆動の自動改修（要望Issueが立ったら自動で修正PR）、
  告知文の定期生成、競合ウォッチの自動レポート。

## 判断基準（撤退ルール）

先に決めておく。感情で延長しない。

- 検証は1アイデアにつき**最大4週間**。数字が動かなければ撤退（撤退＝失敗ではなく学びの記録）。
- 「継続」の条件は事前に数字で書く（例: 2週間でユニーク訪問100、またはStar 5、または問い合わせ1件）。
- 同時に走らせる検証は**2つまで**。

## 最初の一歩（推奨順）

1. **アイデア#1（ギターアプリ公開）を一周させる** — 最も準備ができており、
   「他人に価値が届いた実績ゼロ→1」を最短で作れる。
2. その間に **アイデア#3（経験の棚卸し）** をオーナー自身が行う。
   人生経験こそ競合が少ない領域で、ここの入力はAIには代われない。
3. 1の結果が出たら週次レビュー第1回を実施し、#2以降の順番を決める。

## このシステム自体の改善

週次レビューで「システムの摩擦」（面倒だった手順、迷った判断）も1行記録する。
溜まったらエージェント定義やテンプレートを改修する。システムも検証対象。
